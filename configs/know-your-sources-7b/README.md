# `configs/know-your-sources-7b/` — the 7B grid

108 experiment templates: 72 logical runs = 18 trunks (6 settings x 3 seeds) + 54 cooldown
branches, with each trunk written as 3 segments. Same structure as the 1.5B grid in
`configs/know-your-sources/`, which is untouched.

Generated by `tools/kys7b/generate_configs.py`; **do not hand-edit**. Regenerate with:

```bash
python tools/kys7b/generate_configs.py --out configs/know-your-sources-7b
```

Like the 1.5B templates these are **not runnable as-is** — no `parallelism`,
`micro_batch_size`, `batch_accumulation_per_replica`, `zero_stage`, `sequence_length`,
`tokenizer_name_or_path`, `checkpoints_path`, `resume_checkpoint_path` or `dataset_folder`.
`tools/kys7b/render_config.py` stamps those from `deploy/clusters_7b.yaml`.

## How the 1.5B grid was actually run

Verified **2026-09-02** by reading `config.yaml` out of the published 1.5B checkpoints at

```
/home/jhu/zhuicon1/bvandur1-project/zhuicon1/checkpoints/rewrite-1p5b/seed42/quality_base
```

That tree is an HuggingFace repo snapshot holding three model-only step directories —
`quality_base_seed42_ep1/4768`, `quality_base_seed42_ep2/9537`,
`quality_base_seed42_ep3/14305`. There is no trunk directory and no `latest.txt` in it; the
`ep3` config's `resume_checkpoint_path` names `.../quality_base_seed42_trunk/12875`, which is
where the trunk's latest step lives in the original tree. All three step directories agree on
every deployment field, and each `model_config.json` matches its `config.yaml`
`model.model_config` block exactly.

| | value |
|---|---|
| hardware | B300 (mbs 16 needs ~110 GiB, which does not fit the 74.5 GiB H100 entry in `deploy/clusters.yaml`) |
| `parallelism.dp` / `tp` / `pp` | **4** / 1 / 1 |
| `tokens.micro_batch_size` | **16** |
| `tokens.batch_accumulation_per_replica` | **16** |
| global batch | 16 x 16 x 4 = **1024 sequences** |
| tokens/step | 1024 x 2048 = **2,097,152** |
| `optimizer.zero_stage` | 0 |
| `general.project` | `zhc-1p5b-10b-wsd` |

**This corrects the documentation in one direction and confirms it in another.**
`deploy/clusters.yaml` and `SOP.md` describe an H200 layout at **dp 8 / accum 8** that was
never executed — the real runs were **dp 4 / accum 16**. But the `micro_batch_size: 16` those
documents state *is* the value that ran. `dp` is mathematically free (the micro-batch
partition is consecutive blocks of size `mbs` regardless of `dp`; measured difference exactly
0.000e+00), so absorbing the dp change into `accum` left the objective untouched. That is the
invariant the tooling was built to protect, and it held.

### Consequence for the 7B grid: mbs 8

The 7B grid runs at **mbs 8**, not 16, because 16 does not fit a 7B model on a B300 at
`zero_stage 0` — ~308 GiB estimated against a 241 GiB budget, and still ~244 GiB even with
ZeRO-1 sharding the optimizer state over dp 4. See the `memory_model` block in
`deploy/clusters_7b.yaml` for the arithmetic. At mbs 8 the estimate is 214.6 GiB, 80% of the
card.

The `masked_mean` per-token weighting therefore differs between the 1.5B grid and the 7B grid
by up to **7.04e-4** relative (the measured mbs=8 vs mbs=16 figure in `SOP.md` §1).

**This affects no comparison the experiment makes.** Every six-way between-setting comparison
is within one grid at one mbs, and the two grids already differ in learning rate, warmup,
token budget, embedding tying and parameter count. Within the 7B grid, mbs must be identical
across all 72 runs — `tools/kys7b/render_config.py` still refuses to render when the clusters
in `seed_assignment` disagree, and `tools/kys7b/assert_invariants.py` still pins it, now at 8.

## Parameter count

Using the formula from `model_config_guide.md` §3 with **untied** embeddings:

```
P = 2·V·H  +  L · [ 2H²·(1 + KV/A)  +  3·H·I  +  2H ]  +  H

V = 32000   H = 4096   L = 32   A = 32   KV = 32   I = 11008
```

| term | arithmetic | value |
|---|---|---:|
| `EMBED = 2·V·H` | 2 x 32000 x 4096 (embedding + untied lm_head) | 262,144,000 |
| `ATTN  = 2H²(1 + KV/A)` | 2 x 4096² x (1 + 32/32) = 2 x 16,777,216 x 2 | 67,108,864 |
| `MLP   = 3·H·I` | 3 x 4096 x 11008 | 135,266,304 |
| `NORMS = 2·H` | 2 x 4096 | 8,192 |
| per layer | 67,108,864 + 135,266,304 + 8,192 | 202,383,360 |
| x `L` = 32 layers | 202,383,360 x 32 | 6,476,267,520 |
| `NORM_final = H` | | 4,096 |
| **total** | 6,476,267,520 + 262,144,000 + 4,096 | **6,738,415,616** |

**6,738,415,616 = 6.738e9.** Matches the ~6.738e9 target, so the architecture stands as
specified. (Same formula on the 1.5B config, with the tied-embedding term `1·V·H`, gives
1,504,299,008 — the ratio used below is 6,738,415,616 / 1,504,299,008 = **4.4794**.)

Confirm against nanotron's own `Total number of parameters: …` line on a 1-step dry run before
committing to the full grid.

## Checkpoint disk

Scaling the measured 1.5B figures (21.06 GB per checkpoint = 3.01 GB model + 18.05 GB
optimizer, `HANDOVER.md` §7) by the parameter ratio 4.4794 — equivalently, 2 bytes/param for
the bf16 model and 12 bytes/param for fp32 master + Adam m + v:

| | 1.5B | 7B |
|---|---:|---:|
| model | 3.01 GB | **13.48 GB** |
| optimizer | 18.05 GB | **80.86 GB** |
| **per checkpoint** | 21.06 GB | **94.34 GB** |

Checkpoints per (setting, seed) chain:

| | count |
|---|---:|
| trunk restart points, every 5000 up to 64373 (5000 … 60000) | 12 |
| branch points (21458 / 42916 / 64373) | 3 |
| annealed finals (23842 / 47684 / 71526) | 3 |
| **total per chain** | **18** |

| | per chain | grid (x18) |
|---|---:|---:|
| checkpoints, peak | 1,698 GB | **30.57 TB** |
| after pruning trunk restart points | 566 GB | **10.19 TB** |

18 checkpoints per chain at 94.34 GB each: 6 must be kept (3 branch points + 3 annealed
finals), 12 are trunk restart insurance and can be deleted once their segment completes.
Stripping optimizer state from the 3 annealed finals — the only ones eval needs — takes each
from 94.34 GB to 13.48 GB, bringing a pruned chain to 323 GB and the grid to **5.82 TB**.

ZeRO is not in use (`zero_stage: 0`), and in any case sharding would not change these totals:
the same bytes are written, just split across ranks.

## Rendering and launching one run

Mirrors `SOP.md` §3 with the 7B paths and `--cluster b300`.

```bash
python tools/kys7b/render_config.py \
    --template configs/know-your-sources-7b/quality_first_seed43_trunk1.yaml \
    --cluster b300 --seed 43 \
    --out rendered/quality_first_seed43_trunk1.yaml
```

This writes two files: the config, and a companion `.env` with the wandb wiring. Then:

```bash
set -a; source rendered/quality_first_seed43_trunk1.env; set +a
python tools/kys7b/assert_invariants.py --config rendered/quality_first_seed43_trunk1.yaml --check-resume
torchrun --nproc_per_node=4 run_train.py --config-file rendered/quality_first_seed43_trunk1.yaml
```

`--nproc_per_node=4`, not 8: the b300 entry is dp 4, tp 1, pp 1 on 4 GPUs/node.

Order per (setting, seed): `trunk1 → trunk2 → trunk3`, then `ep1`, `ep2`, `ep3`. Each branch
may start as soon as its trunk segment has written its final checkpoint
(21458 / 42916 / 64373); `ep1` and `ep2` therefore overlap with later trunk segments.

Before the first trunk segment of each chain, seed the trunk directory:

```bash
T=<ckpt_root>/<setting>_seed<S>_trunk          # note underscores: dir stem == run name
mkdir -p $T && cp -al <init_root>/_init_7B_seed<S>/0 $T/0 && echo 0 > $T/latest.txt
```

`cp -al` hardlinks, so seeding all 18 trunks costs no extra disk. Verify afterwards with
`tools/hash_init_checkpoint.py $T/0 --check init_7B_seed<S>.hash.json`.

The rendered banner must read:

```
# global batch: 8 x 32 x 4 = 1024 seq = 2,097,152 tokens/step  [INVARIANT]
```

## Not yet available

Everything below is an unfilled placeholder. Each is marked `# PLACEHOLDER` in the file that
holds it, so `grep -rn PLACEHOLDER tools/kys7b/ deploy/clusters_7b.yaml` finds them all.
Nothing here can be defaulted: the tooling is written to fail loudly rather than run against a
guess.

1. **7B init checkpoints and their hash manifests** — `_init_7B_seed<S>/0` for S in 42/43/44,
   and the matching `init_7B_seed<S>.hash.json` for `tools/hash_init_checkpoint.py`. Do not
   exist. Without them the trunk seeding step above cannot run, and an unseeded trunk starts
   from random init silently.
2. **The tokenized 50B corpora and their token counts** — all six entries of
   `EXPECTED_CORPUS` in `tools/kys7b/assert_invariants.py` are `None`. The corpora have not
   been tokenized, so shard counts are unknown too. `check_corpus_table()` refuses to pass
   while any entry is `None`, and it is not skippable.
3. **The HuggingFace repo name** — `wytro/Know-Your-Sources-7B-tokenized` is the intended
   name, not a verified one; the repo does not exist. Named in
   `tools/kys7b/render_config.py` and `deploy/clusters_7b.yaml`.
4. **B300 `arch` and Slurm fields** — `arch`, `slurm.partition`, `slurm.gres`, `slurm.time` in
   `deploy/clusters_7b.yaml` are `null`. These are already known from the 1.5B B300 runs and
   should be copied from Tianjian's existing launch setup, not re-derived. Phase 0 searched
   the published 1.5B checkpoint tree for a Slurm script, launcher or `.env` and found none —
   it holds only `README.md`, `.gitattributes` and the three step directories.
5. **Measured s/it** — no 7B step has been timed on a B300, so there is no wall-clock estimate
   for the grid.
6. **The memory model** — `static_gib 121` and `per_micro_batch_seq_gib 11.7` in
   `deploy/clusters_7b.yaml` are estimates (the second scales a measured 1.5B H100 figure),
   not measurements. They are good enough to reject mbs 16; they are not a certified fit for
   mbs 8. Profile one real step and replace them.

The four deployer paths — `data_root`, `tokenizer_path`, `ckpt_root`, `wandb.dir` — are
`null` by design in `deploy/clusters_7b.yaml`, as in the 1.5B profile. They are filled in at
deployment, not committed.
